
### SOP: Data Quality Checks

**1. Purpose:**
To ensure the integrity, consistency, and validity of raw data ingested into the `driiiportfolio.raw` BigQuery dataset, preventing propagation of erroneous data into downstream transformations and reports.

**2. Scope:**
This SOP applies to all data ingested into the `driiiportfolio.raw` dataset, specifically `loan_origination_data` and `loan_performance_history`, and any future raw data tables. It covers the execution, interpretation, and response to data quality validation results generated by Great Expectations.

**3. Procedure:**

**3.1. Triggering Data Quality Checks:**
*   **Automated (CI/CD):** Data quality checks are automatically triggered after every data ingestion job (e.g., via `data_ingestion_ci.yml` GitHub Actions workflow).
*   **Manual:** To run checks manually, execute the Great Expectations validation script from the project root:
    ```bash
    great_expectations checkpoint run my_data_quality_checkpoint
    ```
    (Note: Replace `my_data_quality_checkpoint` with the actual checkpoint name if different).

**3.2. Interpreting Validation Results:**
*   **Console Output:** The console will display a summary of successful and failed expectations.
*   **Data Docs:** For detailed results, open the generated Data Docs (usually located in `great_expectations/uncommitted/data_docs/local_site/index.html`). Navigate to the specific validation run for the dataset in question.
*   **Key Metrics to Review:**
    *   `Success Rate`: Percentage of expectations that passed.
    *   `Unexpected Values`: Details on values that violated expectations.
    *   `Summary Statistics`: Overall data profile provided by Great Expectations.

**3.3. Handling Validation Failures:**

**Severity Levels:**
*   **Critical Failure:** Any failed expectation for `expect_column_values_to_not_be_null`, `expect_column_values_to_be_unique` on primary keys, or `expect_column_values_to_be_of_type` for essential columns.
*   **High Failure:** Significant violations in range checks (`expect_column_values_to_be_between`), set membership (`expect_column_values_to_be_in_set`), or referential integrity.
*   **Moderate Failure:** Minor violations in less critical expectations or a small percentage of violations in non-critical columns.

**Action Protocol:**

1.  **Halt Pipeline (Critical/High Failure):** If checks are part of an automated pipeline, a critical or high failure **MUST** halt further data processing (e.g., dbt transformations).
2.  **Alert Stakeholders:** Immediately notify the data engineering team, data owners, and relevant data analysts via email or Slack, including a link to the Data Docs.
3.  **Quarantine Data (Critical Failure):** Move the entire batch of failing raw data to a designated quarantine area in BigQuery (e.g., `driiiportfolio.quarantine.<table>_failed_YYYYMMDD_HHMMSS`).
4.  **Diagnose and Debug:**
    *   Review the Data Docs for specific expectation failures and unexpected values.
    *   Examine the source data for issues.
    *   Check data ingestion scripts for errors.
    *   Consult with data owners to understand potential upstream changes.
5.  **Remediation:**
    *   **Fix Source Data:** Work with data producers to correct issues at the source if possible.
    *   **Adjust Expectations:** If the data characteristics have legitimately changed, update the Great Expectations suite to reflect the new reality (requires approval from data governance).
    *   **Cleanse Data (if applicable):** If remediation is not possible at the source, discuss with data owners if data cleansing is acceptable during transformation (e.g., filtering out bad records, imputing values) and document the decision.
6.  **Re-run Checks:** After remediation, re-run the data quality checks to confirm the issues are resolved.

**4. Roles & Responsibilities:**
*   **Data Engineer:** Responsible for implementing, maintaining, and executing data quality checks; initial debugging; stakeholder notification; and data quarantine.
*   **Data Analyst:** Responsible for reviewing Data Docs, assisting in diagnosis, and providing context on data usage.
*   **Data Owner:** Responsible for data definitions, approving expectation changes, and supporting source data remediation.

**5. Tools/Systems Used:**
*   Great Expectations
*   Google BigQuery
*   GitHub Actions (for CI/CD automation)
*   Email/Slack (for alerts)

**6. Error Handling/Troubleshooting:**
*   **Common Issues:** Schema drift, unexpected nulls, out-of-range values, data type mismatches, duplicate entries.
*   **Troubleshooting Steps:** Validate data against schema, inspect raw data samples, review recent code changes in ingestion or data generation.

**7. Definitions:**
*   **Expectation Suite:** A collection of data quality rules defined in Great Expectations.
*   **Data Docs:** Human-readable HTML documentation generated by Great Expectations, summarizing validation results.
*   **Checkpoint:** A configuration in Great Expectations that bundles an Expectation Suite with a Data Source and an Action List for validation.
